## 结论与范围

在第一轮快速 PNG 的基础上，24 手、25 秒、1500 帧棋谱的三次独立实测中位数从 **50.541 秒降至 44.624 秒，耗时减少 11.71%**，达到本轮至少 10% 的目标。三次平均耗时减少约 11.51%。三组长录像、正常页面导出、完整回归和独立代码审查均通过。

优化的是点击导出后的画面生成、编码及保存阶段；网络传输速度不在本次计时范围内。本机存在耗时波动，结果代表此次重复测量，不能保证任意棋谱、机器负载下每一次都减少 10%。

## 实现

- 两个独立渲染页面同时生成相邻动画画面，按原顺序写出；每手结束时两个页面都推进到最终局面。
- 管道读取与 PNG 解码分别使用一个线程，通过两个容量为 2 的 FIFO 队列交接；编码主线程顺序处理时间戳、重复帧和 MP4 封装。
- 缓冲有界，不累积整段原始视频。代价是增加一个渲染页面的内存，以及少量 PNG/像素缓冲。
- 异常和 EOF 通过 FIFO 传回编码器；失败或取消时停止生产线程，并结束本次导出拥有的渲染进程树。

前端与动画逻辑保持原实现。截图仍是相同的快速 PNG 参数；1080×1192、60 fps、H.264、CRF 18、preset fast、yuv420p 保持不变。

代码：`backend/app/recording.py`、`scripts/render-recording.cjs`。

1. 用户已明确授权执行，按既定方向直接实施；若判断错，可能扩大执行范围，本轮改动均限定于导出。
2. 目录没有 Git 仓库，采用代码快照与 SHA-256 代替分支/提交记录，保留验收及过程文件；代价是回退需要从快照恢复。
3. 单一读取/解码线程未达到目标，增加第二个工作线程和容量为 2 的 PNG 队列；代价是少量缓冲内存。
4. 截图成为瓶颈，增加第二个渲染页面，保留全部截图和动画参数；代价是额外页面内存，结果用真实录像质量检查验证。
5. 独立审查没有重复运行性能、画质和 UI；由执行者实际完成这些验收，否则结论没有证据。现已全部通过。
6. 本轮交付为 Windows，POSIX 进程树终止沿用原行为；代价是未来非 Windows 使用仍需单独验证取消清理。
7. 未扩展没有实际证据的外部协议破坏及系统拒绝终止容错；极端系统故障可能需要人工处理。
