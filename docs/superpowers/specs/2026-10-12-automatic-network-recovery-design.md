# 断网保存与联网自动完成设计

日期：2026-10-12。状态：已按用户确认方向实施并验收，见 output/automatic-recovery-validation/验收报告.md。

## 1. 已确认的目标

用户准备将程序交付企业使用，接受“断网时保存任务，联网后自动完成”。普通使用者无需反复点击重连，网络故障不得丢失已有棋谱。手动重试保留为辅助操作。

成功标准：正常界面发起任务后，网络中断导致任务进入等待状态；网络恢复后，后台自动继续实际识别并完成分析。只有最终识别结果通过现有校验且选区处理完整，才显示完成。存在画面疑点时仍进入既有人工复核流程。

运行前提：后台服务正在运行。关闭网页不取消任务；电脑关机或后台服务关闭期间不执行工作，服务再次启动后自动恢复已授权任务。

## 3. 方案选择与范围

采用现有 SQLite 加持久化检查点及后台调度。相比只增加 HTTP 自动重试，它可以在进程退出、后台重启后恢复；相比独立消息队列，它不增加 Redis、Celery 或新的服务器依赖，适合当前单机部署。

首要覆盖正常网页使用的实际局面复刻流程及单独起始画面识别；同一网络错误分类应用于合法棋谱分析，恢复路径分别保存各自的检测状态。现有本地识别和规则校验继续使用，不改变模型、棋种分类器和录像风格。

本轮不增加第二家模型供应商，不自动改代理或关闭防火墙。原视频已完整保存，断网时可以暂停依赖云端的分析，不要求继续扫描整个视频。联网后补齐全部选区即可，避免缺少前序棋局时继续推断。

## 4. 状态与调度

保留既有任务状态，增加 `waiting_service`（等待服务恢复）和 `action_required`（管理员需处理）。新增持久化恢复字段：是否允许自动运行、操作类型、运行代次、检查点引用、待识别请求引用、尝试次数、下次尝试时间、错误类别、进程租约。

| 触发 | 状态与处理 |
| --- | --- |
| 客户开始分析或识别 | 授权当前操作自动运行，进入 `analyzing` |
| 临时网络故障 | 保存操作，进入 `waiting_service`，释放分析进程 |
| 重试到期 | 调度器在进程空闲时领取任务，重试该操作 |
| 重试成功且结果有效 | 继续分析，不把连接成功等同于分析完成 |
| 明确配置错误或耗尽推理重试预算 | `action_required`，向管理员展示原因与修复入口 |
| 用户主动停止 | 关闭自动运行，标记 `interrupted`，以后不自动启动 |
| 后台重启 | 自动恢复仍授权运行的等待任务和意外中断任务 |
| 用户修改选区、棋盘定位或初始局面 | 作废旧运行代次；旧进程、旧响应不能写入新任务 |

后台调度在 FastAPI lifespan 中启动、关闭，每两秒检查一次到期任务；采用现有单分析进程限制。等待任务不占用唯一分析位置，其他可执行任务可以运行。通过 SQLite 事务领取租约，启动、停止、补写结果均检查运行代次和租约，防止重复进程及旧进程回写。

短暂连接故障重试间隔为 5、15、30、60、120 秒，之后最多每 300 秒一次，加入约 20% 随机浮动。绝对下次执行时间保存为 UTC，重启不重置为立刻密集重试。HTTP 429/503 有有效 `Retry-After` 时不得早于该时间发起下一次请求。

## 5. 保存和恢复的完整性

云端调用前先原子保存输入画面及待请求记录，再以 SQLite 事务保存任务和检查点引用。引用只指向已经完整写入的文件。请求完成后先保存可复用的有效响应，再提交对应棋谱和新检查点。中间崩溃后可重放尚未提交的结果，不重复追加棋谱。

检查点不能只包含 `processed_video_s`。它必须包括：

- 视频时间戳与解码帧标识、选区和棋盘配置版本。
- 当前棋局、身份追踪历史、已提交记录边界、尚未提交的事件。
- 实际局面检测器的基准与候选画面、稳定计时、字形基准、遮挡和离盘状态。
- `TurnReplay` 的 observed、before、pending、color、touched、evidence、violation、note、related、unresolved、boundary 等运行状态。
- 检测器在同一视频帧产生多个事件时的执行阶段，防止恢复时漏掉后续事件或重复处理前一事件。
- 合法棋谱检测流程对应的稳定检测状态及未解决观察结果。

实施裁决：保留现有事件生成器及回合判断，保存不可变原始操作参数、无损请求画面和有效响应日志。恢复通过完整重放原始视频、复用有效响应，重建上述全部检测状态和同帧事件阶段；不序列化Python生成器，也不以固定回看窗口代替历史。已提交记录在重建期间保持原样，重建结果与既有记录不一致时停止并保留原数据。

任务进度仍周期性持久保存，并在每次云端请求前强制保存原始请求；进程重启后可能完整重放已扫描部分，因此有额外本地解码成本，但不得重复成功模型请求或重复提交棋谱。待请求标识由运行代次、操作类型、事件标识、图片摘要、前序棋局摘要和模型请求版本确定。

本地实现的是结果只提交一次，不能承诺云端推理只执行一次：模型请求已经送达但回复丢失时，供应商可能已经处理或计费。成功且已经保存的响应必须复用；状态不明的重试受到独立预算限制。

人工校正以数据库最新记录为准。等待恢复期间允许回放及查看证据；校正、修改设置需先取消自动运行并使旧检查点失效，避免继续使用已被改动的前序棋局。已有人工校正不由自动恢复覆盖。

## 6. 错误分类和费用控制

| 错误 | 行为 |
| --- | --- |
| `ConnectTimeout`、连接中断、临时 DNS 故障 | 自动等待恢复，保留全部进度 |
| `ReadTimeout`、`WriteTimeout`、流式响应中断 | 结果可能不确定；同一操作最多额外重试两次，超过后进入管理员处理状态 |
| HTTP 429、502、503、504 | 自动延后重试，遵守服务端等待时间及推理尝试预算 |
| HTTP 401/403、明确余额不足、模型或接口不存在 | 不进行重复推理；明确提示管理员检查配置、权限或余额 |
| JSON 不完整、候选无法验证 | 与断网分开；有限重新识别后保留证据并进入复核，不伪造棋局 |
| 原视频缺失、磁盘无法保存、检查点损坏 | 停止自动推进，指出具体阻碍，不把未保存数据称为已保存 |

连接建立失败的后台探测可持续进行；已经发送的推理请求不得无限重发。累计请求次数、图片数、返回用量和重试次数如实统计；无法确认的供应商用量标明未知，不填写零费用。

管理员修复配置后可点击“重新检查并恢复”，无需清空棋谱。网络等待时普通用户有可选“立即尝试恢复”和“停止任务”；正常恢复不依赖这两个按钮。

## 7. 网页和后台接口

网页显示“视觉服务暂时不可用，任务和进度已保存，将自动恢复”，同时展示已保存记录数量、等待时长及下次尝试时间。网络等待与不可恢复错误采用不同提示。页面重新打开时读取后台真实状态，不在浏览器内维护恢复任务。

新增恢复接口接收任务版本，作用是把已保存操作提前调度；不调用会清空棋谱的现有 `/analyze` 路径。重复点击返回当前任务状态，不启动第二个进程。主动停止接口同时撤销后台调度和进程租约。

任务列表、详情和前端类型同步增加恢复状态及公开恢复摘要。密钥、图片请求体和供应商原始敏感错误不暴露给网页。现有健康检查继续只表示本地服务存活，不能代替模型真实可用性判断。

录像导出继续要求选区分析完整、棋局已确认；等待和管理员处理状态不得导出为完整录像。

## 8. 已失败任务的接入

旧任务没有完整检查点，不能直接从扫描时间恢复。对已有失败任务仅展示可恢复入口，用户启动恢复前先保存独立备份，再从最后可验证完整棋局及必要前置画面重建状态；旧记录保留并按事件标识去重。无法可靠重建时明确保留原任务，生成独立恢复运行，不直接覆盖已有棋谱。

当前 24 条记录作为真实回归案例，不在开发测试中直接修改。只有用户明确授权该旧任务恢复后才操作生产任务；开发验证使用隔离任务和独立数据目录。

## 9. 验收

1. 同一视频不中断运行与中途断网后自动恢复，最终走棋、时间、局面和疑点结果一致。
2. 网络等待期间保存的棋谱数量、人工校正及证据不减少；恢复没有重复记录或跨过失败步骤。
3. 断网跨越多次自动重试后再恢复，无需点击按钮，任务自动完成。
4. 在请求前保存、响应保存、棋谱提交等边界退出进程，重启后无重复结果；已保存响应不会再次请求云端。
5. 等待期间关闭网页再打开，状态正确；重启后台自动继续已授权任务。
6. 主动停止、连续点击恢复、旧进程晚到结果、修改设置和等待任务切换均不触发重复进程或错误覆盖。
7. 401/403、429、503、读写超时、响应中断、候选无效分别进入正确路径；长期离线不密集请求。
8. 取子未落下、吃子、跨回合边界、短暂复位、同一帧多事件均完成恢复对照，不能产生额外人工疑点。
9. 前端测试、后端相关回归及构建通过；正常 UI 完成“中断—等待—自动恢复—完成”的实际操作。
10. 模拟故障用于可重复验收；真实视觉模型另执行一次受控端到端验证，分别记录联网成功、有效识别、继续分析和结果完整性，不将模型列表查询或本地模拟当作云端识别成功。
