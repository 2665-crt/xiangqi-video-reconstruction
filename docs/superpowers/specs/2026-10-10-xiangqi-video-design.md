# 真人象棋录屏复盘工具：第一版需求与设计

日期：2026-10-10。状态：开发准备文档，尚未实现或完成视频识别验收。

## 1. 目标与已确认条件

用户上传普通真人象棋直播录屏，程序自动提取初始棋局及所有走棋步骤，在右侧虚拟棋盘逐步复现。用于后续演绎与内容制作。

- 第一版开发自己的网页，优先在 Windows PC 浏览器中使用。
- 视频通常棋盘完整可见，视角固定，无剪辑跳步，允许少量手部遮挡。
- 清晰及可以通过前后画面确定的轻度模糊情况应自动识别。
- 有歧义时允许人工确认初始棋局或修正走棋。
- 可使用云端视觉模型辅助分析。原视频保存在本地，模型请求优先发送棋盘关键帧。
- 一步指一方的一次走棋；红黑各一次才是一个回合。
- 当前工作目录没有现有代码和视频文件。用户描述的视频类型作为开发输入条件，不宣称已验证实际样本。

## 2. 第一版范围

包含：视频上传、视频预览、选择对局时间范围、棋盘自动定位及人工调整、初始棋局识别、自动提取走棋、疑点校正、原视频与棋盘联动、逐步与自动回放、保存和重新打开任务。

暂不包含：虚拟棋盘录制与导出、第三方象棋小程序控制、实时直播接入、AI 对弈、自动解说、账户系统、手机专门适配、批量任务。

初期支持单个 MP4/H.264 视频中的一盘棋，其他容器和编码不作为首批验收要求。上传硬限制暂定 2 GiB，作为可调整的产品默认值；测试达不到该规模时不得宣称已验证上限。视频包含多盘棋或开场等待时，由用户选择本次分析区间。

## 3. 技术路线与选择

推荐本地视频处理、局面时序跟踪、象棋规则校验和云端视觉识别结合的路线。单靠整段视频提示词无法稳定提供可核对的逐步证据；训练专用棋子检测模型需要标注数据，第一版先不引入训练流程。

| 模块 | 技术 | 职责 |
|---|---|---|
| 前端 | React、TypeScript、Vite | 上传、布局、步骤列表、回放控制、校正 |
| 棋盘 | SVG | 9 列 10 行交叉点、棋子、移动动画与高亮 |
| 后端 | Python 3.12、FastAPI | 视频任务、分析调度、结果与证据接口 |
| 解码 | PyAV | 使用 FFmpeg 库读取视频元数据及带时间戳的画面 |
| 图像处理 | OpenCV、NumPy | 棋盘定位、透视校正、清晰度、画面差异 |
| 视觉服务 | 可配置的图像输入模型接口 | 初始棋子识别、疑难局面辅助识别 |
| 保存 | SQLite、工作目录内任务文件 | 状态、棋谱、证据和原视频 |

只使用项目内虚拟环境和依赖，服务默认绑定 127.0.0.1；前端开发端口 5278，后端端口 8278。端口为本项目专用，启动遇到占用时报错，不停止其他服务、不自动切换。当前不是 Git 仓库，不创建仓库或提交。

### 模型配置

后端读取 VISION_API_BASE、VISION_MODEL、VISION_API_KEY。接口采用图像输入的 Chat Completions 兼容格式；上线前必须实际测试所选服务兼容性。配置仅保存在后端环境中，前端和日志不得返回密钥。模型版本与费用通过真实样本验证后记录，不预设准确率。

缺少配置时允许上传、预览、棋盘范围调整和人工录入；自动识别按钮明确显示“需要配置视觉模型”，不能返回假棋谱。开发测试可以使用明确标记的测试输入，不能替代用户视频的识别结果。

## 4. 页面与交互

页面标题：象棋视频复盘。主操作：上传视频、开始识别、打开任务。

| 区域 | 内容与操作 |
|---|---|
| 顶部 | 文件名称、当前处理阶段、视频分析位置、已识别步数、待确认数量 |
| 左侧约 45% | 原视频播放器、播放与定位、对局起止时间、棋盘四角调整 |
| 右侧约 55% | 虚拟棋盘、当前走棋方、当前步数、上一手起终点 |
| 棋盘下方 | 上一步、下一步、自动播放、暂停、回到初始局面；步间隔 1/2/3 秒 |
| 步骤列表 | 步序、红黑方、棋子、起终点、视频时间、识别状态 |
| 按需校正区 | 前后证据截图、疑点原因、候选走法、人工修改与确认 |

- 首屏展示上传空状态，棋盘未识别时明确标注“等待视频”，不展示冒充识别结果的棋谱。
- 点击第 n 步显示执行完该步的棋局，并将原视频定位到该步证据时间；第 0 步为初始局面。
- 对照模式按视频时间更新棋盘；演绎模式按步间隔播放确认过的棋谱，原视频不必跟随播放。
- 棋盘统一红方在下；原视频旋转、上下颠倒或镜像通过坐标映射处理，不直接改变原视频。
- 自动播放到未解决疑点前暂停。暂停、跳步和后退取消进行中的移动动画。
- 初始棋局校正可以放置、移除或更换棋子，并设置下一步走棋方。没有可靠初始棋局前不能开始确定性的走棋回放。
- 一般清晰视频不强制人工确认每一步；系统应自动完成后供用户核查。

## 5. 识别流程

### 5.1 视频解码与范围

验证视频可解码，读取宽高、时长和时间基准。始终以解码帧的实际时间戳定位，不以帧序号除以固定帧率替代。分析在用户选定的区间内进行，证据时间保留原视频绝对秒数。

### 5.2 棋盘校准

在首批可靠画面中检测棋盘，建立四角至标准棋盘的透视映射，得到 90 个交叉点。自动结果必须提供可编辑叠层。范围明显包含错误区域或棋盤不可见时提示重新校准。

### 5.3 初始局面

融合多张相邻清晰画面，识别红黑方、棋子类别与位置。不默认标准开局。若从中盘开始，只还原所选区间内可见过程，不推测区间前的走棋。

下一步走棋方结合后续首个可靠变化判断；无法确定时请用户设置。规则校验验证坐标、棋子数量约束、将帅位置等，但合法性不能替代图像证据。

### 5.4 落子检测和身份跟踪

顺序扫描区间内视频，在缩小的棋盘画面上计算变化；对疑似事件保存更密集的前后帧。在手进入、棋子移动和落稳之间进行区分。只有稳定局面发生变化才生成走棋候选。

初始棋子分配稳定身份，结合位置和连续轨迹延续身份；不因某一帧文字模糊就重新随机判断类别。发生吃子时记录目标格原来的棋子。检测器不得把手部变化重复登记为走棋。

快速连走若缺少足够稳定画面，标记疑点并回查更密集原帧；不得用粗采样跳过中间步骤。具体阈值作为配置，必须使用真实视频调试后记录，不先声称普适。

### 5.5 规则校验与多帧消歧

候选至少验证：红黑轮次、起点棋子与身份、终点、己方占位、车路径、马腿、象眼及过河限制、士与将帅范围、炮架、兵卒过河、将帅照面与行棋后己方将帅安全。

结合后续画面验证候选。将军可标记；第一版不根据重复局面裁定长将、长捉、和棋，也不自动推断视频中的认输结果。视频出现摆回棋子或违规动作时，应提示异常，不能编造合法对局。

只有图像、时序和规则支持唯一解释时自动接受。多个可行解释进入 needs_review；视觉模型自报的置信度不能单独成为接受依据。

### 5.6 歧义边界

轻度模糊指当前文字不清，但邻近画面、棋子身份和轨迹足以唯一确定。短时遮挡后若前后证据足够唯一还原，自动恢复；持续遮挡或遮挡期间多步且存在多种解释时保留候选。

未解决疑点之前为确认前缀，之后的步骤可保留为 tentative 草稿，不能显示为全部确认，也不能纳入自动播放。

## 6. 数据与接口约定

### 数据类型

- Color = red | black。
- PieceKind = king | advisor | elephant | horse | rook | cannon | pawn。
- Square = {file: 0..8, rank: 0..9}；file 从虚拟棋盘左到右，rank 从上到下，红方在下。
- Piece = {id, color, kind, square}。
- Position = {pieces: Piece[], side_to_move: Color}。
- Move = {index, color, piece_id, from: Square, to: Square, captured_piece_id: string|null}；index 从 1 开始。
- MoveRecord = {move, video_start_s, video_end_s, status, evidence_ids, position_after}。
- MoveRecord.status = auto_verified | needs_review | corrected | tentative。疑点的 move 与 position_after 可为 null，候选放入 candidates: Move[]。
- Calibration = {corners: [Point,Point,Point,Point], orientation}；Point 为原视频像素坐标，四角按识别出的逻辑棋盘左上、右上、右下、左下排序。orientation = normal | rotated_180 | mirrored | mirrored_rotated_180。
- VideoMetadata = {width, height, duration_s, codec}。
- Task = {id, filename, status, stage, processed_video_s, initial_position, moves, confirmed_prefix_length, revision, error}。
- Task.status = uploaded | analyzing | needs_review | ready | failed | interrupted；视频元数据、区间和校准信息一并持久化。

任务 ID 由服务器生成，原文件名仅供展示，实际存放于 data/tasks/{id}/source.mp4。SQLite 存任务 JSON 及修订号；证据图保存在同一任务目录，结果不依赖浏览器内存。

### HTTP 接口

| 接口 | 请求/返回 |
|---|---|
| GET /api/health | 服务可用与模型已配置布尔值，不返回配置内容 |
| POST /api/tasks | multipart 文件；返回 Task 与 VideoMetadata，完成解码检查 |
| GET /api/tasks | 已保存任务摘要 |
| GET /api/tasks/{id} | Task 完整内容 |
| GET /api/tasks/{id}/video | 支持 Range 的本地视频，允许播放器定位 |
| PATCH /api/tasks/{id}/setup | {revision, start_s, end_s, calibration, initial_position?}；返回更新 Task |
| POST /api/tasks/{id}/analyze | 启动本地后台分析，返回 202 与 Task；同一任务不可重复启动 |
| GET /api/tasks/{id}/evidence/{evidence_id} | 对应证据图，ID 必须属于该任务 |
| PATCH /api/tasks/{id}/moves/{index} | {revision, move}；返回重新校验后的 Task |

前端每 1 秒读取任务进度；服务单进程、一个活动分析任务。revision 不匹配返回 409，避免旧页面覆盖新校正结果。请求校正前必须展示变更，用户点确认才写入；初始局面或某一步改变后，重新校验后续步骤与证据，失去支持的结果转为 tentative。

范围无效、视频不可解码、超过上传上限、模型未配置、模型请求失败等需返回可理解的错误。已产生的证据保留。服务重启后正在分析的任务标记 interrupted，允许用户重新发起分析，不伪装为运行中。

## 7. 使用 SOP

1. 上传视频，查看原视频可正常播放。
2. 一段视频包含多盘时选定一盘的起止时间。
3. 检查自动校准叠层；必要时调整四角。
4. 开始识别，查看实际处理阶段与视频分析位置。
5. 清晰视频直接查看结果；有疑点时查看前后截图、候选，并确认或修改。
6. 对照模式检查步骤与视频；演绎模式逐步或自动复现。
7. 系统保存识别与校正结果，重新打开任务后可继续回放。

| 里程碑 | 完成条件 |
|---|---|
| M0 开发准备 | 写定需求、接口、开发任务和环境报告；不把准备计为软件完成 |

开发不因暂缺样本而停在文档，但 M2 至 M4 的真实效果验证必须有视频输入和可用模型配置；不能以自造棋谱代替。

## 9. 验收

建议至少 5 段完整对局：3 清晰、1 轻度模糊、1 短时遮挡，总计至少 200 次走棋；部分留作未参与调参的验收输入。这是拟定验收集要求，不是现有资产。

- 清晰验收视频：初始棋局与全部走棋正确，不需人工改步，无漏步、重复或顺序错误。
- 可唯一还原的模糊与遮挡片段：自动还原正确，不需人工改步。
- 无法唯一还原的片段：标出准确证据区间并阻止当作确认结果播放。
- 校正后棋谱：每一步起终点、棋子、吃子、走棋方均与参考一致。
- 回放：第 0 步及任意步棋局正确，前进、后退、吃子、跳步、暂停和重新打开一致。
- 记录自动正确步数/参考总步数、漏步数、重复步数、待确认步数、人工修正步数和整局最终匹配情况；不得仅计算被自动接受步骤的准确率来掩盖拒识。
- 记录每局视频时长、处理耗时、模型请求数和提供方返回的计费用量。费用无法精确获取时标“不可用”，不编造金额。
- 未执行上述实测前，只报告功能实现与测试覆盖，不报告已达到视频准确率目标。
